## Stack real (2026-08-11)

- **.NET 10** (`net10.0`) en todos los proyectos.
- **Arquitectura cliente-servidor**: `StockApp.Api` (ASP.NET Core + JWT + Serilog) expone
  la única puerta de acceso a los datos. El desktop (`StockApp.Presentation`) **ya no toca
  la base de datos**: habla HTTP contra la API a través de `StockApp.ApiClient`. Domain →
  Application → Infrastructure quedan del lado del servidor; el cliente es API-only.
- **Persistencia: PostgreSQL** vía Npgsql + EF Core 10. **Ya no es SQLite** — el roadmap
  original (Incremento 2) se escribió cuando la app era desktop-only con SQLite local; eso
  cambió por completo en la migración cliente-servidor (ver tabla de hitos posteriores).
- **UI**: Avalonia 12.0.5 + DataGrid 12.0.1.
- **Auth**: JWT + BCrypt.Net-Next.
- **Distribución**: Velopack 1.2.0.
- **Versión del desktop**: 0.1.5. Tags publicados: `v0.1.2`, `v0.1.4`, `v0.1.5`.
- **Tests**: 2845/2845 en verde sobre 8 proyectos (Domain 141, Application 691,
  Infrastructure 398, Api 446, ApiClient 208, Licencias 8, Presentation 853, UiTests 100).

## Incremento 1: Fundaciones ✅ COMPLETADO

**Plan detallado:** `docs/plans/2026-06-08-01-fundaciones.md`

Estructura de la solución con las 4 capas (Domain / Application / Infrastructure /
Presentation), app Avalonia que abre una ventana, SQLite cableado vía EF Core con
`AppDbContext` mínimo, y los cuatro proyectos xUnit con el ciclo TDD operativo. No
contiene ninguna feature funcional: es el andamiaje sobre el que se construye todo.

**Dependencias:** ninguna (punto de partida).

## Incremento 2: Dominio + Persistencia + Backups ✅ COMPLETADO

**Plan detallado:** `docs/plans/2026-06-08-02-dominio-persistencia.md`

Entidades del dominio (Usuario, Producto, Categoria, Proveedor, UnidadMedida,
MovimientoStock, LogAuditoria y sus enums), DbContext con Fluent API, primera migración

## Incremento 3: Auth + Usuarios + Autorización ✅ COMPLETADO

Login con BCrypt (hash + sal, nunca texto plano), sesión en memoria mientras la app
corre con soporte de cierre/cambio de sesión sin reiniciar. Asistente de primer
arranque para crear el Admin inicial (no hay contraseña por defecto). ABM de usuarios
solo para Admin: alta, edición, baja lógica (`Activo = false`). Autorización verificada
en la capa Application antes de ejecutar cualquier acción sensible; la UI refleja el
estado pero no es la frontera de seguridad.

**Dependencias:** Inc 2. Va antes del catálogo: la seguridad es el cimiento sobre el
que se construyen las features operativas.

**Resultado:** implementado con **128 tests verdes** (Domain 6 / Application 38 /
Infrastructure 56 / Presentation 28). Incluye UI de login y asistente de primer
arranque. Pasó revisión de seguridad.

> **Nota 2026-08-11:** el modelo de autorización por rol fijo (Admin / Operador) descrito
> acá se extendió a permisos configurables por operador — ver "Permisos por operador" en
> hitos posteriores.

## Incremento 4: Catálogo ✅ COMPLETADO

ABM completo de productos (con SKU, código de barras opcional, precio costo y venta,
stock mínimo, baja lógica), categorías, proveedores y unidades de medida (tabla
editable, no enum). Búsqueda de productos por SKU, código de barras y nombre.
Auditoría automática de cambios de precio y de altas/bajas de productos (registra en
`LogAuditoria` con el usuario que hizo el cambio).

**Dependencias:** Inc 3 (el catálogo requiere usuario autenticado y autorización).

**Resultado:** implementado con **309 tests verdes** (Domain 39 / Application 77 / 
Infrastructure 109 / Presentation 84). 16 tasks en 4 bloques (Domain + Migración / 
Application / Infrastructure / Presentation) + fix de búsqueda case-insensitive + 
3 fixes de verificación (W1/W2/S1). Decisiones clave: pantallas separadas con menú 
lateral (Productos para Admin+Operador, tablas maestras solo Admin); permisos separados 
GestionarProductos / GestionarTablasMaestras; baja lógica con `Activo` en Categoría, 
Proveedor y UnidadMedida; auditoría de todo el catálogo; unicidad en Proveedor.Nombre,

Pasó verificación independiente (sdd-verify): 0 CRITICAL. Plan detallado: 
`docs/plans/2026-06-09-04-catalogo.md`.

## Incremento 5: Movimientos de stock ✅ COMPLETADO

Registro transaccional ACID de entradas y salidas: en la misma transacción se inserta
el `MovimientoStock` y se actualiza `StockActual` en `Producto`, con los motivos
Compra / Venta / Ajuste / Merma. Validación de stock no negativo (advertir con
confirmación, no bloquear). Función de recálculo de stock desde los movimientos como
red de seguridad ante descuadres.

**Dependencias:** Inc 4 (los movimientos operan sobre el catálogo).

**Resultado:** implementado con **389 tests verdes** (Domain 41 / Application 113 /
Infrastructure 126 / Presentation 109). 25 commits en 4 bloques (Domain + Migración /
Application / Infrastructure / Presentation) + 3 fixes post-verify (WARNING-01: diálogo
modal Avalonia real para ConfirmacionService; WARNING-02: rollback robusto con método
virtual; HM-04: normalización FechaHasta a fin de día). Decisiones clave: atomicidad
vía single SaveChanges sobre mismo DbContext; auditoría dentro de la transacción del
movimiento (no usa IAuditLogger/AuditService); test de rollback con constraint NOT NULL
+ segundo context para verificación real de EF. Deuda diferida a Inc 6: Permisos.VerMovimientos
para rol ReadOnly; StockAnterior/StockNuevo persistidos en la entidad para fidelidad histórica
del running balance. Pasó verificación independiente (sdd-verify): 0 CRITICAL. Plan detallado:
`docs/plans/2026-06-10-05-movimientos-stock.md`.

## Incremento 6: Reportes + Auditoría ✅ COMPLETADO

Cinco reportes solo para Admin, todos exportables a CSV: valorización de stock (a
costo y a venta), stock por categoría, historial de movimientos por producto

**Resultado:** implementado y mergeado a main vía PR #1. Ver más adelante "Cache de

## Incremento 7: Distribución ✅ COMPLETADO (código), validación real parcial

Empaquetado con Velopack como self-contained (runtime .NET 10 incluido): `Setup.exe`
en Windows y `AppImage` en Linux. Actualizador in-app con fallback dominio propio →
GitHub público y UX por severidad (normal / important / critical con modo degradado).
Licenciamiento: licencia offline firmada con criptografía asimétrica, atada a la
máquina (machine fingerprint cross-platform), pantalla de bloqueo sin licencia válida,
y herramienta CLI interna (nunca distribuida) para generar licencias. También incluye
el **token de reset de Admin firmado** (último recurso de recuperación de acceso, spec
§5.1): reutiliza la misma infraestructura criptográfica asimétrica del licenciamiento.

**Dependencias:** Inc 6. Va al final: se empaqueta y licencia un producto terminado,
no un andamiaje.

**Resultado:** Fase A (empaquetado + actualizador) y Fase B (licenciamiento + reset
firmado) están **completas en código y validadas en WSL**. Nunca se corrió el ciclo
completo de empaquetado + instalación + update en **Windows real** ni en un **Linux

## Deuda técnica conocida, no bloqueante

Aceptada explícitamente durante el desarrollo de "Permisos por operador" — no
bloquea el uso normal de la app, pero queda anotada para una vuelta futura:

- **Doble GET a `/auth/permisos` al navegar a Inicio.** Cada navegación dispara dos
  requests: uno desde `ShellMainViewModel.OnNavegacionCambiada` (corre en toda
  navegación) y otro desde `InicioViewModel.CargarAsync`. Ninguno rompe nada (ambos son
  best-effort e idempotentes), pero es tráfico duplicado en la pantalla más visitada.
  La solución correcta es deduplicar requests en vuelo en el ApiClient — merece su
  propio cambio, no un parche puntual.
- **12 ViewModels sin ningún `catch` en sus comandos**: `ShellMainViewModel`,
  `FilaGastoEditableVm`, `FilaIngresoEditableVm`, `CalendarioPagosViewModel`,
  `ControlPoaViewModel`, `LibroCajaViewModel`, `MovimientoHistorialViewModel` y los
  cinco de `Reportes/*`. Aceptado porque el manejo central de excepciones mitiga lo
  peor: aunque la excepción escape del comando y termine en el crash log, el usuario
  igual ve el aviso — no es silencio total, y no quedan flags de carga trabados. Los
  cinco de `Reportes/*` son prioridad si se retoma, por ser los de mayor probabilidad
  real de 403 (`ReportesEndpoints` usa `RequirePermiso`).
- **Caso angosto de 3 pasos que puede re-otorgar permisos ya revocados.** La condición
  `Count == 0` en el fix de sincronización de permisos no distingue "nunca tuvo filas"
  de "un Admin le vació los permisos a propósito". Secuencia alcanzable: `PUT
  /usuarios/{id}/permisos` con lista vacía → promover a Admin → degradar a Operador →
  el fix ve `Count == 0` y siembra los 9 permisos iniciales, otorgando permisos que un
  Admin había revocado explícitamente. Angosto (tres pasos deliberados) pero real. La
  solución limpia exige una columna/flag tipo `PermisosConfigurados` en `Usuario` o
  `PermisoUsuario`. Sin test que lo cubra.
